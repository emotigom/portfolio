01

Identity & Ownership

클라이언트가 보낸
사용자 ID를 신뢰하지 않습니다.

FastAPI에서 Supabase 세션을 확인한 뒤, 요청의 소유자를 session.user_id로 정합니다. DB 요청에도 같은 호출자의 토큰을 전달해 RLS가 적용되도록 했습니다.

세션 검증 코드 ↗ 저장 계층 코드 ↗ 회귀 테스트 ↗
observation_store.py발췌
# 검증된 세션의 토큰과 신원
"Authorization": f"Bearer {session.access_token}"

json={**values, "user_id": session.user_id}

회귀 테스트는 클라이언트의 임의 ID가 세션 ID로 대체되는지 확인합니다. Mock HTTP 기반 테스트 코드이며 현재 운영 RLS 검증은 아닙니다.

02

Data Lifecycle

접근 만료를
삭제 작업에 의존시키지 않습니다.

DB가 30일 만료 시각을 정하고 임의 연장을 거부합니다. 소유권과 만료 조건을 RLS에서 함께 검사하고, 만료된 행의 물리 삭제는 별도 정리 작업으로 분리했습니다.

Deep Dive / Account Lifecycle늦게 끝난 계정 삭제가 새 세션을 지우지 않도록호출자 한정 삭제 API와 비동기 세션 정리의 경합 처리+

어떤 문제였나요?

이전 세션의 삭제 후 정리 작업이 진행되는 동안 같은 사용자의 토큰이 갱신되거나 다른 계정으로 바뀔 수 있습니다. 이전 작업이 끝났다는 이유만으로 새 세션의 상태와 저장 정보를 지우면 안 됩니다.

어떻게 나눴나요?

삭제 API는 검증된 세션의 사용자만 대상으로 삼습니다. 브라우저의 정리 작업은 요청 당시 토큰과 세션 맥락을 확인하고, 더 새로운 세션을 덮어쓰지 않도록 했습니다.

이전 세션 → 삭제 요청 → 정리 대기그 사이 새 세션이 도착이전 작업 완료 → 새 세션은 유지

아래 E2E는 합성 세션과 mock API 기반 경합 검사입니다. 실제 Supabase 계정 삭제·cascade 전체의 운영 검증과 구분합니다.
